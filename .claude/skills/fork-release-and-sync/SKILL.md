# Operate the sync and release automation

All commands use `--repo balakumardev/orca`. In a fork `gh` otherwise targets the parent repo stablyai/orca, which you must never write to.

## The upstream sync (`custom-sync.yml`)

Runs every 3 hours (`23 */3 * * *`) and by hand. Inputs for a manual run: `ref` (an upstream tag, branch or sha to rehearse with; empty means the newest stable release), `base_branch` (default `custom`) and `skip_agent`.

Jobs: `detect`, `merge`, then either `gates0` (clean merge) or the model rounds `agent1 > gates1 > agent2 > gates2 > pick3 > agent3 > gates3`, then `open-pr`, then `land`.

- `detect` picks the HIGHEST semver tag matching `^v[0-9]+\.[0-9]+\.[0-9]+$` that is not a draft or prerelease (upstream tags are not ancestors of each other, so publication order says nothing). It stops quietly when that tag is not newer than `custom/BASE` or when a PR in ANY state already exists for `sync/<tag>`: an open one is the answer, a merged one means `custom/BASE` moved on, and a closed one means "no" and is never reopened by the automation (reopen it by hand if you change your mind), with ONE exception: an open PR of that tag that is stale (`custom` moved on) and untouched automation output is replaced (the "stale sync PR" bullet below). Open sync PRs for older tags are closed and their branches deleted only after the new PR exists.
- `merge` merges with an explicit base. Upstream release tags are not on one lineage, so a plain `git merge <tag>` conflicts in dozens of files nobody touched. The script merges a synthetic "link" commit whose tree is the new tag and whose parents are the new tag and the old base tag, which makes the old base the merge base: only OUR changes are replayed. Scripted steps follow: delete upstream's workflows and `dependabot.yml`; keep our side for our-wins paths (`custom/**`, `.github/workflows/custom-*`, `.github/pull_request_template.md`, `CUSTOM.md`, `CLAUDE.md`, `.claude/skills/fork-*`; one list, `OUR_WINS_PATTERNS` in `lib.sh`, test `test-scaffolding-paths.sh`); write the new tag to `custom/BASE`; take upstream's version of any conflicted file that no customization touches and of generated files; regenerate `pnpm-lock.yaml` with `--lockfile-only --ignore-scripts --ignore-pnpmfile` (then restore the pnpmfile checksum line, so frozen installs still pass). The merge runs with `-X find-renames=30%` (git's default 50% treats a file that upstream moved AND trimmed as "deleted by them" plus a new file: a conflict kind the model may not touch, and our edit lost; v1.4.261 moved two edited files at 46% and 48%). A conflicted file is settled from upstream's side only when OUR side did not change it, judged by the index stages (`our_side_changed` in `sync-merge.sh`: stage 2 differs from stage 1), never by `our-files.txt`, which lists the OLD paths: judged by path, six moved files of v1.4.261 had our edits replaced by upstream's version without a word. A file upstream really deleted that we edited stays `deleted-by-them` (or `deleted-by-us`), and the AGENT decides it (below); test `test-sync-merge-renames.sh`. The merge also runs with `merge.directoryRenames=false`. When upstream empties a directory (v1.4.263 split `tests/e2e/helpers/`), git's default relocates the files WE added there and raises `CONFLICT (file location)`: a stage-2-only entry that `conflict_kind` calls `other` (human only), so no agent round and no gate ran, and PRs #39 and #40 both stopped as `[needs manual merge]` on three files that had no markers at all. Our files now stay where our code imports them. Git never rewrites an import, so after the scripted resolutions `repoint-moved-imports.mjs` repoints the relative and `@/` imports of OUR code files (those that differ from upstream and sit in no conflict) at the files upstream moved: an exact rename (same object id), else the one same-named file the release added; it reads no blob (the sync clone is blobless). v1.4.263 left 176 broken imports in 87 of our files, which `pnpm tc` reports as hundreds of TS2307 lines that a repair round sees cut to 7000 bytes (PR #37 stayed red this way). What it cannot prove (a removed file, an ambiguous name) stays as it is and is listed in `repointed-imports.json` of the `round-0` artifact and in a caveat; a script failure only adds a caveat. Test `test-repoint-moved-imports.sh` (its control proves the fixture still triggers git's file-location conflict).
- The model rounds (`custom-agent.yml`) only run for conflicts in files our customizations own. Round 1 resolves with the cheap model (edit scope: the conflicted files), round 2 repairs using the real gate output (scope: the conflicted files plus the files our customization commits own, never `custom/**`, `.github/**` or upstream CI), or, when round 1 ran out of turns with files still holding markers (no gates ran), CONTINUES that candidate: the prompt (`#@ resume` in `custom/agent/prompt.txt`) lists only the files still unresolved. Round 3 uses the stronger model: `pick3` (a script, `pick-repair-base.sh`) chooses the best candidate of rounds 1 and 2 (`round_score` in `lib.sh`: failed gates; an unresolved candidate scores 1000 plus the files still unresolved, so a resolved one always wins and, among unresolved ones, the one that got furthest does; a tie goes to the later round) and round 3 REPAIRS or CONTINUES it with the round 2 scope; only when no earlier round left a usable candidate (a crash, a key leak, resolved with gates that never reported) does round 3 start again from the merge (`retry`, conflicted files only). `pick-round.sh` publishes by the same score. Never restart a partly resolved merge: v1.4.261's round 1 resolved 16 of its 22 model files (9 files were left, 3 of them for a human), the restart threw that away and Pro left 14, and the later, worse round was published (PR #35, an estimated $5 for a worse result). The prompt's list of our customizations is `customization_log` in `lib.sh`: commits with the trailer that change product code (commits that only touch our-wins paths or `.github/` are left out), cut to 6000 bytes; the check output of a repair or retry round holds the tail of EVERY failing gate (each cut to its last 4000 characters, the whole block to 28000 bytes; it was one shared 7000 bytes, which the first gates filled, so in v1.4.265 round 3 never saw the e2e typecheck ratchet output that names the missing exports), both with `trunc_bytes` (see the trap below). There is NO turn cap (`claude -p` runs without `--max-turns`): a round ends when the model is done or after the 1 hour wall clock (`timeout`, 3600 s, every mode and tier; the job's `timeout-minutes` is 90; the PR says "hit the wall-clock limit; edits kept; gates decide"). Measured on v1.4.261: a Flash turn costs about $0.01 and takes about 6.7 s, a Pro turn about $0.07 and 16.8 s, so a one hour round costs at most about $8 on Flash and $15 on Pro (v1.4.265 on Flash: 400 turns, $3.70, 29 minutes). A round killed by the clock has no token or cost figures (the CLI writes its JSON only at the end), and keeps its edits; the next round continues from them. The hour (it was 30 minutes) comes from v1.4.265: 43 conflicted files, round 1 and round 2 used 29 and 24 minutes, and round 3 was killed with nothing written, so every gate but typecheck stayed red. The reason there is no turn cap: a cap of 70 turns stopped round 1 of v1.4.261 at 16 of its 22 model files (about 4.4 turns a file), and the fixed merge leaves 31 files for the agent. Modify/delete conflicts (`deleted-by-them`, `deleted-by-us`) are the agent's to decide, with no human step: the prompt lists them with what each side did, the agent keeps the file (untouched, or edited to fit upstream's new code) or replaces its WHOLE content with the single line `DELETE-THIS-FILE`, and only `sync-merge.sh finish` removes the file (`is_delete_request` in `lib.sh`: only for these two kinds, a delete line in any other file leaves it unresolved). The decision is recorded in the facts (`decision`: kept or deleted) and shown in the PR's conflict table; a file left untouched is kept, and the gates and the repair round judge it. Every other kind (a rename conflict, a file git placed after a move: no markers, one side's version in the tree) is the agent's too, decided the same way (keep it, fixed to fit upstream, or `DELETE-THIS-FILE`); no kind is left to a human any more (a stage-2-only conflict of kind `other` used to skip every round and every gate, PRs #39 and #40). The prompt's rule (Bala, 2026-11-19): keep BOTH sides' changes whenever that is correct; when they cannot both stand, pick the side the agent itself recommends, finish the file and say why in an `UNSURE:` line; never leave a file for a human. A round with nothing left to resolve is SKIPPED: the plan says `skip`, the model is not called, and the PR shows "skipped". Gates still decide whether `land` merges: a red gate is never merged automatically. The PR lists the files a repair round edited outside the conflicted ones (the resolution diff does not show them), and names the test files among them: a repairing model can turn a gate green by weakening a test. The job has a read-only token, the key is in the environment of one step only, no repository code runs before that step, scripts enforce which files may change, and a key-leak scan discards any round whose output contains the key. The model never runs a gate and its text is never treated as a verification result. The agent's shell (since the sandbox change): the agent can run `pnpm tc`, `pnpm check:e2e-typecheck-ratchet`, `oxfmt`, `oxlint` and `vitest run <files>` (never the whole suite, `vitest related` or the Playwright specs; the prompt says so), because it runs in a COPY of the tree as another OS user without sudo (`agent-sandbox.sh setup`, a key-less step: creates `agentrun`, installs the pinned pnpm under root-owned `/opt/agent-tools`, copies the tree to `/opt/agent-sandbox/repo`, runs `pnpm install` there as that user). The API key stays with the runner user: `agent-round.sh run` pipes it on stdin to `agent-key-proxy.mjs` (127.0.0.1, only `/v1/`, fixed DeepInfra upstream, client auth dropped) and gives the agent a dummy token and the proxy's address, so no command it runs can read the key (a child could otherwise read its parent's `/proc/<pid>/environ`, and vitest executes upstream's third-party test code). After the run a key-less step (`agent-sandbox.sh collect`) copies back ONLY the contents of regular files: no symlink, nothing under `node_modules` or `.git`, nothing the real tree's `.gitignore` ignores, never `pnpm-lock.yaml`, nothing through a symlink of the real tree; a tracked file the agent removed is removed. The real tree and its `.git` are never exposed to the agent, so scope enforcement in `finish` is unchanged. If the sandbox step fails the round falls back to the old read-only tools (`git`, `grep`, `ls`); `AGENT_SANDBOX=1` without a set-up sandbox stops the step (the agent never gets a shell outside the sandbox). Tests: `test-agent-key-proxy.sh`, `test-agent-sandbox-collect.sh`, `test-agent-round-sandbox.sh` (fake sudo, stub model) and the manual Linux one `test-agent-sandbox-linux.sh` (needs docker; proves the OS-user separation). Not proven without a real runner: the GitHub image's sudo setup, `/home/runner` permissions and `kernel.yama.ptrace_scope` (a paid rehearsal from `custom` shows them). Nor can it run a formatter (its tools are read-only git, grep and ls plus file edits), so `finish` runs `oxfmt --write` on our code files (`format-our-files.sh`, the oxfmt version the merged lockfile pins, installed by `install-oxfmt.sh` in a key-less step before `finish`; skips fork scaffolding, upstream CI and files with markers) and lists the files it changed as a caveat; without `OXFMT_BIN` it does nothing. Test `test-format-our-files.sh`.
- Gates (`custom/scripts/run-gates.sh`, shared with `custom-pr-gates.yml`): `hygiene lint-caps install typecheck lint format unit unit-related localization e2e-ratchet e2e`. Gate scope: on a sync, the files our customizations touch; on a PR, the files the PR changes plus our own files. The e2e gate runs the Playwright specs inside that scope (and skips when there are none), on macOS because one pixel-layout assertion differs on Linux. Every result is a real exit code: each gate function runs in a subshell with `set -e` really on (`in_gate_shell` in `run-gates.sh`: a background subshell that is waited for; the earlier `( set -e; ... ) || rc=$?` silently turned errexit off, so a gate reported only its last command and the lint and format gates could never fail), `check_errexit` runs a failing canary through the same path before every gate and stops the run if errexit is off (a changed `in_gate_shell`, or `run_gate` called from an `||`, `&&` or `if` list), test `test-run-gate-errexit.sh`. Our own `custom/scripts/*.mjs` are in the sync scope, so they must pass oxlint and oxfmt like product code. There is one exception to the real exit code: when vitest exits 1 although no test and no test file failed, because of an "Unhandled Errors" section whose originating files are all unit test files outside the gate scope, the gate re-runs just those files once. If that re-run passes the gate passes and records a warning naming the file (the first run threw an unhandled error that did not reproduce); in every other case it stays red (`custom/scripts/unit-flake.sh`, test `test-unit-gate-flake.sh`). The Playwright screenshots and error context of a failed e2e gate are the artifact `e2e-results-<round>` (`e2e-results-pr` on a pull request), kept 7 days.
- Unit-related gate and its known traps (2026-11-15, PR #28): `unit-related` runs `vitest related` over the source files a PR changes, so a PR that touches a widely imported module selects 800+ test files (CI 633 s, cap 1500 s) that smaller PRs never run, and shows up every test that is fragile on a 2-vCPU runner. Four were met and handled:
  - `tests/e2e/cross-version-wire/**` needs upstream release tags (`git rev-parse v1.4.229` fails in a PR clone; fetching them downloaded over 1 GB). `config/fork-pr-gate-test-excludes.mjs`, read by `config/vitest.config.ts` and switched on by `FORK_PR_GATE=1`, excludes them; `custom-gates.yml` sets it for pull requests only. The name has no `ORCA_` prefix on purpose: `run-gates.sh` unsets every `ORCA_*` variable (hermetic), and the first version of this switch was silently dropped that way (the CI log showed it set, vitest never saw it). Test a gate switch through `run-gates.sh`'s own scrub, not by exporting it in your own shell. Sync mode never runs `unit-related` (`gate_unit_related` skips unless `MODE=pr`), and local runs are unaffected. Only add a file there for a missing environment that the CI log names, not for a flaky result.
  - The `session-search-*` tests got no search worker ("unavailable") in some runs and not in others on the same commit: they import `session-search-worker.test-fixture.ts`, and in the shared-worker vitest project (`isolate: false`) their `vi.mock` is order dependent. `@orca-isolated-worker` in that fixture keeps every importer in its own worker (upstream's own opt-out in `vitest-shared-worker-files.mjs`, which follows a test's imports of test-support files). Isolating every file instead (`ORCA_VITEST_ISOLATE_EVERY_FILE=1`) also fixed them but took 1110 s against 684 s, so it is not used.
  - `terminal-send-ordered-input.test.ts` waited 100 ms for a refusal while pushing a 9 MiB and a 25 x 700 KB payload; it failed at those two lines in both CI runs and once in a local run under load, and passes alone. Its two `waitFor` ceilings are now 5000 ms (a pass returns as soon as the refusal arrives, and the held write is only released in `finally`, so a missing refusal still fails).
  - A PR that changes any file under `config/scripts/**` made `vitest related` select the WHOLE suite (7538 files): `config/vitest.config.ts` lists `**/config/**` in `forceRerunTriggers`, and vitest returns every spec when a related path matches one (`filterTestsBySource`). `unit-related` hit its 1500 s cap (exit 124) with no failing test (PR #33, 34 minutes to a red status). `config/fork-pr-gate-force-rerun-triggers.mjs`, applied in `config/vitest.config.ts` and switched on by `FORK_PR_GATE=1`, drops that trigger in PR mode so the module graph picks the tests (PR #33: 2 of 7490). A red `unit-related` at about 1501 s with no failed test is this cap, not a test: read `exit_code` (124) in the `gates-pr-static` artifact and `Affected N of M` in its log. Measure a fan-out without running tests: `vitest list --filesOnly --changed <base>` prints every spec when a trigger fired. Two limits: a test that runs a config script by path (as `sign-mac-app.test.mjs` runs the verifier) is not selected by the graph when only that script changes; the `unit` gate's directory scope covers tests in the same folder. And `**/src/packages/**` is still a trigger (left as upstream, not measured, because upstream may list it for built package output): a PR that touches `src/packages` still fans out to the whole suite. NEVER run `vitest related` on such a file locally: it fills swap and hangs the Mac (2026-11-16).
  - The gate scripts come from the base commit, but workflow files and `config/` come from the PR, so a change to them takes effect in the PR that makes it.
- `open-pr` pushes only `sync/<tag>` (or `sync-test/*` for rehearsals), opens the PR, never force-pushes and runs no repository code. Two more jobs since the self-healing change: it closes the stale PR it replaces (next bullet), and on a RE-RUN of the job (`GITHUB_RUN_ATTEMPT > 1`: GitHub re-runs a failed job AND every job that depends on it, so `rerun-infra-failures.sh` re-running a failed gate also re-runs `open-pr` and `land`) it ADOPTS the open PR whose head is already this merge commit instead of dying on `gh pr create`: title, body, labels, draft state (`gh pr ready`, or `--undo` when the gates now fail) and the gate statuses are refreshed, then `land` can fire. A different candidate than the open PR's head cannot be pushed over the branch (no force-push), so then the job fails as before. Test `test-open-pr-replace.sh` (real git and a local bare origin, stub `gh`).
- **A stale sync PR is replaced, not waited on** (`stale-sync-pr.sh`, sourced by `detect-release.sh` and `open-pr.sh`; evidence: PR #43, where `custom` moved while the sync ran, `land` refused, and `detect` then stopped on "PR already exists" for ever). `detect` classifies the existing PRs of `sync/<tag>` and, only when ALL of these hold, reports `replace_pr`, `replace_head` and `orphan_branch=true` and carries on with a fresh sync from the current `custom` on the same branch name: the PR is OPEN, same repository, against `custom`, opened by the automation, and the only open PR of that branch; its HEAD is untouched automation output (the merge commit `sync-merge.sh` made for THIS upstream commit: author and committer are `AUTOMATION_EMAIL`, `Orca-Custom-Patch: upstream-sync`, `Upstream commit: <sha>`, two parents, the second being the automation's `Link upstream` commit whose first parent is that upstream commit; both read through `git/commits/<sha>`, never `commits/<sha>`, which computes the commit's files against its first parent: the whole upstream delta, 26606 files on v1.4.265); it is STALE (the merge's first parent is a proper ancestor of the tip of `custom`: `compare/<P>...<tip>` says `ahead`; a compare of `custom...head` would carry the whole upstream release as a diff); and fewer than 3 earlier PRs of the branch were closed by the automation. Not satisfied: the PR is left alone and the reason is in the `detect` summary ("left alone: its head commit ... is not the merge commit this automation made ..."). **Why the head and not "every commit of the PR is by the automation"** (the first idea): GitHub lists every upstream commit between the two release tags as commits of the sync PR, written by upstream's people; upstream's own `release: vX` commit has the SAME bot name and email as ours; and the REST list stops at 250 commits. A per-commit author scan therefore always refuses or proves nothing (the sync clone is full, the local one in this repo is grafted and hides it). Anything a person adds (a fix, `git merge origin/custom`, the web "Update branch" button: PR #43's `dc0f46fc61f`) becomes the new head and fails the check. The close is `open-pr`'s, not `detect`'s (`detect` has a read-only token, and the sync takes up to hours): `open-pr.sh` re-reads the PR and requires it still open, same repo, base `custom`, bot author, head branch `sync/<tag>` and HEAD == `replace_head`; if anything changed (a person pushed while the sync ran) NOTHING is closed, deleted or pushed, the job ends green with a warning and a summary line, outputs no `pr_number` (so `land` is skipped) and the next `detect` leaves that PR alone. Otherwise: close with the comment `superseded: custom moved on, syncing again` plus the hidden marker `<!-- custom-sync:superseded -->`, delete the old branch (the orphan-branch path), plain push, create. If the run dies after the close, the next `detect` finds a marker-closed PR under the cap and syncs again by itself. Attempts: only a CLOSED PR whose LAST comment is the marker, written by the automation, counts; a PR closed any other way (or a person's comment after the marker, or the marker written by a person) is a "no" and stops the search as before; 3 such PRs stop it ("cap 3", so a branch gets at most 4 PRs) and a third stale PR is left for a person. A non-stale open PR, a merged one, two open ones, or an open one with a person's commit also stop it, as before. Rehearsals (`is_test`, a throwaway base branch, a bare sha) make no PR lookup at all. Not covered: the retirement of OLDER tags' PRs (`SUPERSEDE`) is unchanged and still ignores a person's commits there (a newer release makes them obsolete). A person who works on a stale sync PR without pushing yet can still lose the branch: push early, or close the PR yourself. Tests: `test-detect-stale-sync-pr.sh` (every guard has its own case, plus the cap and the marker rules; the stub serves a PR commit list with upstream's people in it, so a per-commit scan would fail it) and `test-open-pr-replace.sh`; both take `SCRIPTS_DIR=<dir>` to run against another copy of the scripts.
- `land` (`custom/scripts/land-sync-pr.sh`) is the only job that merges or dispatches, and only for a real run: a scheduled run, or a dispatch with an EMPTY `ref`, on refs/heads/custom, base branch custom, an upstream release tag. A rehearsal fails the job's `if:` (skipped, no token issued) and the script refuses the same conditions again. It lands the PR when the PR is not a draft, the chosen round's custom-gates job succeeded with `failed == 0` (the output counts a crashed gate job; `gates.json` files do not) and `custom` is still the commit the sync started from. Then: check-run `gates / result` (success, real gate result in the summary) on the PR head, `gh pr merge --merge --match-head-commit`, verification (merge commit parents are the old tip and the head; custom's tip is that commit), then ONE `gh workflow run custom-release.yml --ref custom -f sign=true -f notarize=true -f publish=true` (skipped when a dispatched run for that commit exists). Red gates or a moved `custom`: exit 0, reason in the job summary and a PR comment, PR left for a human. An error: the job goes red and nothing is dispatched. Permissions: only this job has `checks: write` and `actions: write`. Test: `custom/scripts/test/test-land-sync-pr.sh`.
- An open sync PR for the SAME tag (for example one the old flow made, such as sync/v1.4.259) stops `detect` ("a PR in any state exists") unless it is stale AND untouched automation output (see the stale-PR bullet: then it is replaced). A PR with a person's commit, a current one (custom has not moved) or one over the cap stays: the sync never lands that tag by itself and never opens a second PR for it. Merge it by hand with a merge commit once its gates are green: the push to `custom` starts the release. A NEWER tag opens a new PR and `open-pr.sh` closes the older open sync PRs (and deletes their branches) before `land` runs.
- When `land` declines because `custom` moved, nothing needs doing: the next scheduled sync closes the untouched PR and syncs again (the stale-PR bullet above); the decline comment says so, and a push to the branch (or closing the PR) opts out. For the other declines (red gates, a draft, a refused merge) the PR stays open and the reason is in the job summary and a PR comment. Merge it by hand with a merge commit once its gates are green (a push to the PR branch runs the PR gates), or wait for the next upstream tag, which retires it.

### PR kinds

- Normal: title `Sync upstream <tag>`, labels `upstream-sync` (plus `agent-resolved`, `needs-review`).
- `[gates failed]`: a draft; the body says which gates failed.
- `[needs manual merge]`: a draft with conflict markers committed and `custom/UNRESOLVED-MERGE.txt` listing the files. Resolve it: `gh pr checkout <n> --repo balakumardev/orca`, edit the listed files until no `<<<<<<<`, `|||||||`, `=======` or `>>>>>>>` line remains, `git rm custom/UNRESOLVED-MERGE.txt`, commit, push, then mark the PR ready and drop the prefix from the title.
- `[test]`: a rehearsal draft. Close it and delete its branch.

PRs opened with the workflow token do not trigger `pull_request` workflows, so the job posts commit statuses named `gates / static`, `gates / e2e` and `gates / result` from the real gate results. The required check on `custom` is pinned to the GitHub Actions app, which a commit status cannot satisfy: `land` posts a check-run of that name (a check-run made with the workflow token belongs to the Actions app).

### Review checklist for a sync PR

Read the gate table; the conflict table (which file, resolved by script, by the model or left for you; "Hunks" counts conflict hunks); the `--remerge-diff` block (what the resolution decided); the caveats (files within 10 lines of a lint cap, gates skipped or passed only after a flake re-run, out-of-scope edits the script reverted, files a repair round edited that were not conflicted, a round that ran out of turns); and the model's own report, which is labelled unverified. The first line says whether merging starts a release: it is read from the `on:` block of `custom-release.yml` (a `push:` trigger that can fire for the base branch means yes). Look at the sidebar by eye: no test covers where a new upstream section lands. A CAUTION block about a key leak means rotate `DEEPINFRA_API_KEY`. **Merge with a merge commit.** Squash and rebase are disabled because they would drop the upstream merge base.

### Rehearse without touching `custom`

```
gh api -X POST repos/balakumardev/orca/git/refs -f ref=refs/heads/test/sync-base -f sha=$(gh api repos/balakumardev/orca/commits/custom --jq .sha)
gh workflow run custom-sync.yml --repo balakumardev/orca --ref custom -f ref=<upstream ref> -f base_branch=test/sync-base
```

Use `-f skip_agent=true` to skip the model. The model job (environment `agent`) only runs from `custom`; from a feature branch it is skipped and the PR opens as `[needs manual merge]`. Afterwards close the `[test]` PR and delete the `sync-test/*` branches and `test/sync-base`.

## Infrastructure re-runs (`custom-rerun-infra.yml`)

Every 15 minutes (and by hand: `gh workflow run custom-rerun-infra.yml --repo balakumardev/orca -f dry_run=true` prints what it would re-run and sends nothing) `custom/scripts/rerun-infra-failures.sh` re-runs the FAILED jobs (`gh run rerun <id> --failed`) of our own runs whose failure was the runner's fault. Evidence: GitHub-hosted macOS arm64 e2e jobs repeatedly ended `cancelled` after 15 minutes with the annotation "The job was not acquired by Runner of type hosted even after multiple attempts"; re-running the failed job fixed it every time, and in a sync run it left the candidate without an e2e result so `land` never fired. The workflow is a thin caller (own `GITHUB_TOKEN` in `env`, `actions: write` + `checks: read` + `contents: read`, concurrency group, no secrets, no expression in a `run:` block); the script's only write is the re-run.

- **Which runs**: completed, `failure` or `cancelled`, of `custom-pr-gates.yml` or `custom-sync.yml` (`custom-agent.yml` and `custom-gates.yml` are called by those two, so their jobs are part of those runs), updated in the last 6 hours (runs are listed from the last 48 hours: a sync can start hours before it ends), `run_attempt < 4` (attempts 1 to 3 are re-run, a persistent outage ends after the fourth), from this repository (a fork's PR run is not ours to re-run).
- **What counts as infrastructure**: a failed job whose OWN check-run annotations (`GET /check-runs/<job id>/annotations`; for an Actions job the check-run id is the job id) match, case-insensitively, one of `not acquired by Runner`, `lost communication`, `received a shutdown signal`, `runner has received a shutdown`, `The self-hosted runner`. Jobs are read with `filter=latest` (newest attempt only). At least one such job is needed.
- **What blocks a re-run** (any one): another failed job that is a real failure; a job cancelled for exceeding `timeout-minutes` (its annotation says so, so it counts as real); a failed job with no annotation that is not `cancelled`; an annotation that cannot be read; a run cancelled by a newer run of its concurrency group (`higher priority waiting request`); for `custom-pr-gates` a pull request that is not open any more, whose head is not the run's `head_sha`, or that cannot be read, and a run with no pull request attached (a re-run attempt joins the PR's concurrency group `custom-pr-gates-<PR>` with `cancel-in-progress: true`, so re-running the run of an OLD head would cancel the run a newer push started and leave the newer head without `gates / result`; `custom-sync`'s group has `cancel-in-progress: false`, so a re-run there can only displace a pending scheduled run, which comes back in 3 hours). NOT blocking: a job `cancelled` because a sibling failed or a person cancelled (no annotation, or only "The operation was canceled" / "The run was canceled"), and the `result` job of `custom-gates.yml`. That last one is a deliberate reading of the rule "a derived failure is not a real one": in a PULL REQUEST run `result` exits 1 whenever `static` or `e2e` did not succeed (it is the required check `gates / result`), so in the very evidence case (e2e "not acquired") `result` is `failure` with the plain annotation "Process completed with exit code 1." and a strict "any non-infrastructure failed job blocks" rule would never re-run it. A real gate failure still blocks, because it shows as `static` or `e2e` itself.
- **custom-sync is limited to jobs whose re-run is coherent**: `detect`, `merge`, `gates (round 0)` and `gates (round 3)` (their `static`, `e2e`, `result`), `open-pr`, `land`. GitHub's own rule ("GitHub also re-runs the jobs that depend on them"; jobs not re-run keep their outputs): re-running the gates of round 1 or 2 also re-runs `agent2`, `pick3`, `agent3` (paid model rounds, up to about $15 for Pro) and would pick another candidate than the one `open-pr` already pushed; re-running an agent round or `pick3` likewise. Those cases are left for a person (the log says "left for a person"). A re-run of round 0 or round 3 gates re-runs only `open-pr` and `land`, and `open-pr.sh` adopts the PR its first attempt opened (see its bullet), so `land` fires. If the new gate results make `pick-round.sh` choose another round than attempt 1 published, `open-pr` fails at the push as it always did.
- **custom-release.yml is excluded** (the task allowed either choice). A release has outside effects (a tag, a GitHub release and an asset the installed apps download), its `plan` job reserves the version number N once, and a late re-run of an OLD run could publish an old commit under a number a newer run also planned (the publish job refuses an existing tag, but only after the newer run published first). A failed release is visible in Actions; re-dispatch it: `gh workflow run custom-release.yml --repo balakumardev/orca --ref custom -f sign=true -f notarize=true -f publish=true`. A guarded inclusion (infrastructure fault in `plan` or `build`, `publish` not started, `head_sha` still the tip of `custom`) is possible if releases keep failing this way.
- **Unverified until a real infrastructure failure happens** (the paths cannot be exercised end to end here): that the "not acquired" message is exposed through the check-run annotations API (the annotation is visible in the UI; the same endpoint serves other runner annotations, but nobody has read this one through it); that the `GITHUB_TOKEN` of a scheduled run may call the re-run endpoint (it needs `actions: write`, which the job has); the exact job names of called workflows in the jobs API (`gates (round 0) / e2e`; the allow-list and the `result` rule depend on that `<caller> / <job>` shape, and a different shape makes the script skip, never over-re-run); that a re-run attempt really joins the concurrency group and cancels a newer run (the premise of the PR-head guard; if it does not, the guard only costs a re-run that a person must click); that `pull_requests[0].number` and `head_sha` of a `pull_request` run are the PR and its head (a fork's run has none and is skipped anyway); that `git/commits/<sha>` (used by `stale-sync-pr.sh` instead of `commits/<sha>`, which diffs the whole upstream delta) answers for the 2-parent merge within the time budget, as `land-sync-pr.sh` already relies on. If the first real `cancelled` run is not re-run, read the job summary of the `custom-rerun-infra` run: every skipped run says why.
- Scheduled workflows in a public repo stop after 60 days without repository activity (see traps): if this one goes quiet, re-enable it. Test: `test-rerun-infra-failures.sh` (`SCRIPTS_DIR=<dir>` works there too).

## Releases (`custom-release.yml`)

Dispatch: `gh workflow run custom-release.yml --repo balakumardev/orca --ref custom -f sign=true -f notarize=true -f publish=false`. Inputs: `sign` (default true), `notarize` (default true, needs sign), `publish` (default false, needs sign). A push to `custom` also starts it (`on.push.branches: [custom]`, no paths filter) with sign, notarize and publish all true. The `plan` job resolves the three values once (`inputs.*` is empty on a push): dispatch uses the inputs, a push on refs/heads/custom is true/true/true, anything else false/false/false, and `build` and `publish` read only `needs.plan.outputs.*`. Never read `inputs.*` anywhere else in that file. Events caused by the workflow token (its merge, its push) start no `push:` workflow, so the sync's `land` job dispatches the release itself. The concurrency group is per ref (all runs on `custom` share one, a run from another branch has its own) and keeps one pending run: a burst of pushes to `custom` releases only the newest.

- Jobs: `plan` (version) > `build` (macos-15 arm64; `environment: release` only when `sign=true`) > `publish` (only when `publish=true`).
- Version: base tag from `custom/BASE`; `N` is the highest `N` among existing `v*+custom.*` release tags (global across bases) plus one, minimum 4. Tag `v<base>+custom.<N>`; asset `Orca-<version>-arm64-mac.zip` plus `<asset>.sha256` and `manifest.json` (`version, tag, base, upstream_commit, built_from_sha, signed, team_id, notarized, asset, sha256, size`). Read asset URLs from `gh release view --json assets`; never assemble them from strings.
- A feature branch can only run `sign=false` (no environment, so no secrets); a signed run only works from `custom`. Measured on hosted runners: about 7 min unsigned, 9 min signed, about 3 more for notarization. Notarization waits up to 40 minutes (`NOTARY_TIMEOUT`); exit code 3 means Apple still had the submission "In Progress" (the ticket stays valid: check `xcrun notarytool info <id>`, do not resubmit).
- Verify a build before publishing: `gh run download <run> --repo balakumardev/orca -n orca-release`, then `shasum -a 256 -c`, `ditto -x -k`, `codesign --verify --deep --strict`, `xcrun stapler validate`, `spctl -a -vvv -t exec` (expect `source=Notarized Developer ID`).
- Roll back: `gh release delete <tag> --cleanup-tag --yes`. `N` is computed from existing release tags, so the next release reuses a deleted `N`: if anyone could have installed it, ship a higher `N` instead of deleting.

## Traps that cost time

- Scripts run under `set -euo pipefail`. A pipeline that ends in a command that stops reading early (`head -c N`, `grep -q`, `sed -n 'Np;q'`, `awk ... exit`) kills a producer that still has output: it dies of SIGPIPE, the pipeline exits 141 and `set -e` ends the script. The first paid rehearsal died this way in the step that builds the prompt, right after "merge outcome: conflicts", because `git log ... | head -c 6000` met a customization log longer than 6000 bytes (the long bodies of the pipeline-fix commits). Appending `|| true` is wrong (it also hides a real failure). Use `trunc_bytes N` from `lib.sh` (it reads all of its input), a here-string (`grep -q x <<<"$v"`), or capture first and cut after (`v="$(cmd)"; v="${v%%$'\n'*}"`). `test-trunc-bytes.sh` proves the helper with a 10 MB producer and scans every script and workflow for the shape (a line whose producer is known to be tiny may carry a `pipe-ok: <why>` comment); `test-agent-round-prepare.sh` runs the prepare step on a log far over 6000 bytes. Inside `$(...)` bash turns `set -e` off, so a test producer must report its failure by its exit status.
- A called (reusable) workflow only receives a secret the caller passes BY NAME (`secrets: NAME: ${{ secrets.NAME }}`), even if it exists only in the called job's environment; the calling job cannot declare `environment`. Never use `secrets: inherit` here.
- `workflow_dispatch` needs the workflow file on the default branch; `--ref <branch>` then runs that branch's copy.
- Scheduled workflows in a public repo are disabled by GitHub after 60 days without repository activity: if the sync goes quiet, re-enable it in the Actions tab.
- `+` survives in tags, release URLs, `gh release download` and asset names. A draft release has no git tag until it is published.
- Do not register self-hosted runners on this public repo (a fork PR could run code on them); hosted macOS runners are free for public repos.
- A release that moves thousands of files (v1.4.261 against v1.4.258: 8041 files added, 10270 deleted) multiplies every conflict: v1.4.259 had 6 files for the model, v1.4.261 has 31 for the agent (30 content conflicts and 1 modify/delete) once the merge pairs the moved files. Read `merge.log` and `conflicts.tsv` of the `round-0` artifact first: a `deleted-by-them` file whose basename exists elsewhere upstream is a move below the rename threshold, not a deletion (`git -c diff.renameLimit=20000 diff -M10% --name-status <old> <new> -- <old path> <new path>` prints its similarity). To reproduce a sync locally without the model, run `sync-merge.sh start` (env as in `custom-agent.yml`) in a detached worktree of the base commit; it needs the upstream tag fetched (`git fetch --depth=1 https://github.com/stablyai/orca.git tag <tag>`).
- Where to look when a run fails: the job logs, and the artifacts `round-0` / `round-N` (the candidate plus `sync-facts.json`), `gates-<round or pr>-static` and `gates-<round or pr>-e2e`, `e2e-results-<round or pr>` (only when the e2e gate failed), `sync-review`, `orca-release` and `build-diagnostics`.
- Branch protection on `custom` (check the repo settings for the current state): a pull request is required (0 approvals), the required check `gates / result` is pinned to the GitHub Actions app, admins are included, force-push and deletion are blocked, merge commits only. The Actions app cannot be a bypass actor on a personal repo, so nothing running as github-actions[bot] can push to `custom`: it can only merge a PR whose required check is green, which is what `land` does.
